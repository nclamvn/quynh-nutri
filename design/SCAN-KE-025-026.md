# SCAN REPORT – KE-025/KE-026

Date: 2026-07-30

## TECH STACK

- Language: TypeScript, strict Next.js build
- Framework: Next.js 16.2.12 App Router, React 19
- Styling: Tailwind CSS 4 and shared tokens in `src/app/globals.css`
- Database: Neon PostgreSQL through Prisma 7
- Auth: Clerk, household ownership resolved from the authenticated user
- State: authenticated `StoreProvider` hydrated from Neon
- Tests: Vitest, Playwright, production readiness and bounded local load gates

## RELEVANT MODULES

- `src/data/repo/household.ts`: creates a blank household on first sign-in and
  owns household-scoped persistence.
- `src/ui/store.tsx`: hydrates canonical household state and exposes mutations.
- `src/ui/components/AppShell.tsx`: common authenticated shell.
- `src/lib/assistant/week-plan-proposal.ts`: stable AI proposal contract.
- `src/ui/components/AssistantSheet.tsx`: full before/after diff and explicit
  confirmation required by KE-017.

## PATTERNS TO REUSE

- Resolve `householdId` on the server, never accept it from the browser.
- Keep E2E hermetic with the in-memory repository adapter.
- Reuse `PageContainer`, shared controls, rose interaction semantics and
  botanical success semantics.
- Treat proposed plans as drafts until the user confirms the complete diff.

## GAPS

1. No first-party lifecycle event contract or activation funnel.
2. A newly created household has no members but enters the full app without a
   short guided setup.
3. No atomic onboarding mutation, retry-safe completion or measurable handoff
   to the existing weekly proposal flow.
4. Product measurement must not collect names, health details, free text or
   raw Clerk identifiers.
